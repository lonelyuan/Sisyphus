# 分类学：话题领域树 + 平衡维护

分类是知识库最重要的问题。这里定义**话题领域树**（文件夹 = 博客栏目）怎么长、怎么保持均衡。文章类型（`type`）是**正交**的另一轴，见 [types.md](types.md)。

## 两轴，别混

| 轴 | 载体 | 作用 |
|---|---|---|
| **话题领域** | 文件夹 `folder`（本文件） | 卡片"讲什么"；= 博客大分类栏目 |
| **文章类型** | frontmatter `type` + 标签（[types.md](types.md)） | 卡片"怎么维护/怎么链接"；理论/新闻/现状/最佳实践/个人 |

一张卡 = 恰好一个领域（folder）+ 恰好一个类型（type）。**`folder` 值一律以 `kb/` 开头**。例：`folder=kb/web-security, type=theory` 的《SQL 注入原理》；`folder=kb/work-mihoyo/state, type=state` 的《我司 WAF 现状》。

## 领域树（初始，已播种 `kb/*/index.md`）

所有领域都在 `kb/` 下；**`write_knowledge_note` 的 `folder` 必须以 `kb/` 开头**。下面是当前已维护的主领域与子话题，不是禁止新增子文件夹的白名单。

```
kb/web-security               Web 应用层攻防
kb/network-infra              网络架构 / 检测设施 / SOC-SIEM-SOAR / 云与主机基建
kb/network-infra/identity-system
                              身份源 / 目录服务 / 认证 / 授权 / SSO / MFA / 访问策略
kb/ai-redteam                 LLM 攻防 / Agent 安全 / 红队方法 / 靶场（目标方向）
kb/work-mihoyo/state          我司现状（仅本地，type=state）
kb/work-mihoyo/best-practice  企业最佳实现（理想，type=best-practice）
kb/personal                   个人 / 非技术（隔离）
```

每个领域夹有一张 `index.md` = 该栏目的 MOC/落地页（Quartz 的 section 首页）：一句领域范围 + 子话题占位 + 卡片列表。**新建/更新卡片后要顺手更新对应 `index.md` 的卡片列表**，保持"一眼看清这个栏目有什么"。

## 文件夹不是知识图：先织关系

文件夹只负责粗粒度栏目，真正的组织由 MOC 与 `[[wikilink]]` 完成：

- 每个高频工作域要有一个短标题母节点/MOC，如 `工作地图`、`安全基建`，用于表达主线和分支。
- 每张主题卡至少接入一个母节点，并链接 1–4 个有明确语义的邻居；关系应能解释为父子、依赖、对照、实例或 gap。
- 禁止把十几张互不链接的卡平铺在同一目录，再把目录列表当作“网状知识”。
- 禁止用长标题编码层级，例如 `米哈游 YDY 计算平台能力与安全边界`；应写成 `YDY`，由 `work-mihoyo/state`、标签和 `[[工作地图]]` 提供上下文。
- 一轮对话不会天然产生一个新节点。先找它属于哪颗结晶的 H2 小节，只有独立可检索且多处复用时才升级成卡。

## 分类决策流程（建卡前定 folder）

1. 命中现有领域和母节点？→ 用它，并先确定要长入哪颗已有结晶。
2. 像现有领域的**子话题**？→ 仍放该领域夹；若该领域已到拆分阈值（见下），先拆子文件夹再放。
3. 都不像、但未来会反复出现？→ **提议一个新领域节点**（告诉用户："建议新增领域 `xxx`"），获认可后建 `kb/xxx/index.md`。
4. 一次性、太宽泛、不值得，或说不清与现有节点关系？→ 不建卡（留给普通对话或归并成小节）。

**绝不**因为"想不到放哪"就丢 `kb/` 根目录或塞 `misc/`——那是上一版"不成体系"的病根。

## 平衡维护（信息熵稳定）

目标：任何时刻打开任一栏目，条目数适中、层次分明，不出现"一个栏目 100 条、另一个 2 条"。

> ⚠️ **不是机械的"红黑树式平衡"——知识图谱不是搜索树，别为凑数字而拆并。** 要的是：父节点抽象一致、同级节点粒度接近、分支不过宽、深度不过深、高频查询路径短、大变更可解释可回滚。下面的阈值是**触发思考的信号，不是硬指标**。

**阈值（经验值，可调）：**
- 单领域（同层）卡片 **>~12** → **拆**：从中提炼 2–4 个子话题，建子文件夹，把卡片移进去，更新 `index.md`。
- 某领域长期 **<2** 且无增长 → **并**：上并到父领域或相邻领域，删空夹。
- **同主题多张碎卡** → **结晶化（defragment）**：过[原子性双筛](crystallization.md#原子性双筛它配单独一张卡还是只是某颗结晶的一节)不过关的簇合成一颗结晶，`delete_note` 清冗余。见 [crystallization.md 去碎片化例程](crystallization.md#去碎片化defragment例程)。
- 同层子话题数量尽量 **3–7 个**（太多则再抽象一层，太少则合并）。

**重排是安全的**：`[[wikilink]]` 按标题解析、**与路径无关**，移动 `.md` 到别的文件夹**不断链**。所以放心移动；移动后只需更新受影响的 `index.md`。

> ⚠️ 已知限制：`delete_note`（删卡+剪枝索引）已可用，合并碎卡后清冗余走它。但**移动**文件后 `knowledge_notes` 索引的 `path` 仍会与实际不一致（Obsidian 里的 `.md` 才是链接真相，索引为辅助检索）；索引漂移不影响 Obsidian 使用与博客导出；若要移动后索引一致，等 `move_note`/`reindex` 工具（fast-follow）。合并卡时用「`write_knowledge_note` 写新卡 + `delete_note` 删旧卡」这条路径，索引天然一致（不涉及 mv）。

## rebalance 例程（周期 / 触发）

用户说"整理知识库 / 重排 / rebalance"，或每周一次：

1. `list_knowledge` 全量 → 按 folder 前缀统计各领域卡数，画一棵带计数的树。
2. 对照阈值，列出**拆/并/结晶化/新增领域**建议（说清哪些卡移到哪、哪些碎卡并成哪颗结晶）。
3. 用户认可后执行：移动 `.md`（`mv`）或合并卡（`write_knowledge_note` 写超集 + 改 `[[wikilink]]` + `delete_note` 删旧碎卡）+ 更新相关 `index.md` + 顶层 `kb/index.md`。
4. 回报一行：`🌳 重排：web-security(15→拆 注入7/认证5/访问控制3)· 🔮 personal 雅思(3→1)…`。

信息熵直觉：让每个栏目承载的信息量相当、命名互斥、一眼可辨——不是死守数字，是"打开任一栏目都清爽"。
